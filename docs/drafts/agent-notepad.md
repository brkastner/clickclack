# Agent notepad implementation plan

**Status: Selected for implementation. This documentation change does not implement, verify or deploy it.**

Task: [KAS-893](https://linear.app/kashub/issue/KAS-893/show-openclaw-agent-notepads-in-clickclack).

The canonical behavior is specified in [SPEC.md](../../SPEC.md#agent-notepad-kas-893). The selected summary, steps and validation below are preserved verbatim.

## Summary

Implement a read-only OpenClaw agent notepad in ClickClack, using explicit server-owned conversation bindings, an authenticated gateway adapter, and the existing HTTP/WebSocket and Svelte UI conventions. Keep changes in the supplied ClickClack worktree. OpenClaw and pi-clickclack are reference-only; do not deploy or change live configuration.

## Selected implementation steps

1. Add a narrow optional OpenClaw integration under apps/api/internal/config and a dedicated server adapter. Inspection found no existing gateway connection in ClickClack configuration; pi-clickclack is a Pi session bridge, not the OpenClaw transport. Use operator-supplied server-only bindings keyed by workspace plus channel/DM ID, with gateway connection identity, exact agent ID and session key captured from authoritative OpenClaw routing. Validate duplicates and incomplete/ambiguous bindings, fail closed when unmapped, and never derive targets from names or accept arbitrary gateway targets from browsers. Prefer configuration over a new database table. Keep credentials out of public feature responses, errors and logs.
2. Implement the gateway WebSocket handshake, advertised-capability checks, typed progressCard.get response validation, and supported session observation lifecycle using persona-workstation's gateway protocol, progress-card handler, session-observer identity helpers, sessions-subscriptions.ts and native session-progress-cards.ts as references. Inspect the observer delivery/auth guards before selecting the subscription calls; distinguish list subscription from target observation and participation authorization. Subscribe before reading, retain owner-scoped wire identity, and refetch matching progressCard.changed invalidations rather than interpreting them as content. Coalesce in-flight refreshes with one trailing refresh, fence requests by connection/target generation, refetch after reconnect, and release obsolete observation ownership. Never invoke progressCard.put.
3. Add conversation-scoped notepad read/watch/unwatch contracts to apps/api/internal/httpapi, packages/protocol and packages/sdk-ts using existing generation conventions. Follow workflow_snapshots.go authorization: current actor, messages:read, dms:read where applicable, GetChannel/GetDirectConversation and workspace access. Extend the established authenticated WebSocket lifecycle for narrowly targeted invalidations/status, not a workspace-wide stream of card contents. Recheck current conversation access for reads, subscription creation and event delivery, remove watches on disconnect/revocation, and include connection/binding identity in server cache keys. Return distinct unsupported, unmapped, denied, unavailable and successful-empty outcomes.
4. Add a focused notepad lifecycle module under apps/web/src/lib/chat and a collapsible panel integrated into ChatApp.svelte beside the existing workflow panel conventions. Fetch on opening and reconnect; reset immediately on target changes and reject late responses. Render markdown through the existing sanitized message-rendering path, optional pending/in_progress/completed steps and update time. Provide loading, empty, denied, unsupported/unmapped and disconnected states; never present an unverified cached snapshot as current. Treat null cards from authoritative refetches as empty, including after reconnect. Keep the entry point unavailable for unbound/Pi-only conversations. Support keyboard controls, both themes and narrow layouts without changing composer or persona behavior.
5. Add adapter, HTTP/WebSocket authorization, client lifecycle and UI regression tests with synthetic gateway fixtures. Exercise two gateway/agent/session identities, matching and unrelated events, duplicate/out-of-order invalidations, invalidation during a read, switching during a read, reconnect, clearing, malformed replies, missing methods, auth failures and disposal. Prove forbidden users receive neither reads nor invalidations, including access revocation, and ensure credentials never appear in browser-visible payloads or logs.
6. Document the binding format, how to obtain exact routing identities, credential and gateway observation requirements, configuration/activation instructions and lifecycle behavior. Run focused tests followed by repository-required checks. Capture isolated Electron desktop and narrow-layout evidence in light/dark themes, retaining chat/composer/attachments/persona/Pi workflow regression coverage. Where an already-authorized live mapping is available, perform only a read and qualify advertised methods/auth/observation against that gateway. Otherwise report the exact live qualification gap while delivering fixture evidence. Handoff commits/worktree, mapping and transport choices, check results, UI captures, live-versus-fixture evidence, activation steps and confirmation that nothing was activated.

## Selected validation

- Run focused Go tests for the new adapter and HTTP/WebSocket handlers, plus existing workflow/agent-activity authorization tests. Run focused web lifecycle/rendering tests and SDK/protocol generation/type checks.
- Run pnpm check (the repository check:changed alias runs the same full gate) and git diff --check. If implementation requires SQL despite the configuration-first design, edit canonical SQL and regenerate with pnpm generate:sqlc rather than editing generated storedb files.
- Use an isolated authenticated fake gateway to prove owner/target separation, subscription lifecycle, reconnection/remote clearing and current-access enforcement; malicious markdown must not execute scripts.
- Verify the panel in a task-owned Electron instance at desktop and narrow sizes in both themes. Record fixture-only cases separately from any read-only live session proof. Do not restart, deploy, publish, alter live configuration or mutate a live notepad.

## Boundaries and evidence

OpenClaw remains the source of truth. This is a read-only panel, not a Pi-side notepad or a change to chat/session ownership. OpenClaw and pi-clickclack remain reference-only. Implementation stays in the supplied ClickClack worktree.

Documented local source behavior is not proof of live gateway compatibility. Live qualification requires an already-authorized mapped session and read-only checks of advertised methods, authentication and observation. If unavailable, deliver fixture evidence and identify the exact remaining live qualification gap. Do not mutate a user's live card to manufacture evidence.

This document records selected work, not test results or activation. Implementation, testing and evidence collection belong to later workflow stages. Deployment, service restarts, publishing and live configuration changes are not authorized by this plan.
